# 계획 먼저, 구현은 승인 뒤

사용자는 코딩 초보다. 되돌리기 어렵거나 개인정보가 걸린 작업은 **무엇을 어떻게 바꿀지 먼저 읽고 승인**할 수 있어야 한다. 이 스킬은 (1) 언제 승인이 필수인지, (2) 계획서를 어떻게 쓰는지, (3) 어디에 저장하는지를 정한다.

## 1. 승인이 필수인 작업 (하나라도 해당되면)
| # | 해당 조건 | 예 |
|---|-----------|-----|
| 1 | 개인정보·민감 데이터를 새로 받거나 바꾸거나 지움 (`DATA.md` S2·S3 항목, 사진·서명·동의) | 동의 서명 팝업, 회원 삭제 |
| 2 | 서버(Supabase) 테이블·RLS 정책·함수·버킷·키 변경 | 공유 링크 삭제 함수 |
| 3 | 지우기·옮기기·초기화처럼 되돌리기 어려운 데이터 동작 | 기기 데이터를 서버로 이전 |
| 4 | 결제·구독·로그인 | Play 구독 검증 |
| 5 | 배포 설정 변경 | 버전 체계, 서비스워커, 패키지명, manifest |
| 6 | 규모가 큼 | 바뀌는 파일 3개 이상, 단계 4개 초과, ADR 변경 |

해당 없음 → **한 줄 계획**(무엇을 어느 파일에서 바꿀지)만 보여 주고 바로 진행한다.
판단이 애매하면 승인이 필수인 쪽으로 간다.

## 2. 계획서 양식 (`docs/PLANS/YYYY-MM-DD-제목.md`)
```
# 계획: {제목}
상태: 초안        (초안 → 승인됨 → 진행 중 → 완료 / 폐기)
요청: {사용자가 한 말 그대로}
작성일: YYYY-MM-DD   승인일: -

## 한 줄 목적
(사용자 입장에서 무엇이 달라지나)

## 범위
- 하는 것: …
- 하지 않는 것: … (떠오른 아이디어는 BACKLOG)

## 바뀌는 곳
| 파일 / 서버 항목 | 무엇을 |
|---|---|

## 데이터 영향
(DATA.md 의 어떤 항목이 생기거나 바뀌나. 등급·보관·삭제. 없으면 "없음")

## 위험과 되돌리는 법
| 위험 | 일어날 때 | 되돌리는 법 |
|---|---|---|

## 단계
1. {할 일} — 확인: {무엇이 되면 끝인가}
2. …

## 확인이 필요한 질문 (최대 3개, 각각 추천 답 포함)
1. …

## 승인 기록
(승인 시 "승인됨 YYYY-MM-DD" 와 사용자가 바꾼 점)
```

## 3. 진행 규칙
1. 계획서를 저장하고 **표 형태 요약 + 질문**을 보여 준 뒤 멈춘다. "승인", "OK", "진행해" 같은 명확한 답을 받기 전에는 코드·서버·설정을 바꾸지 않는다.
2. 사용자가 수정을 요구하면 계획서를 고치고 다시 보여 준다. 승인 후 범위가 달라지면 계획서에 변경을 적고 다시 승인받는다.
3. 승인되면 상태를 `승인됨`, 구현을 시작하면 `진행 중`, 끝나면 `완료` 로 바꾼다. 실제 구현이 계획과 달라졌으면 "실제 구현" 메모를 남긴다.
4. 계획서 저장과 상태 변경도 커밋에 포함한다 (`docs: 계획 …`).
5. 서버 변경(항목 2)은 계획서에 **배포 방법**(어떤 명령·화면으로 올리는지)과 **되돌리는 법**을 반드시 적는다. 모르면 `{확인 필요}` 로 남기고 질문에 넣는다.
6. 가짜 데이터(홍길동·010-0000-0000)로만 시험하는 방법을 단계에 포함한다.

## 하지 말 것
- 승인 전에 "일단 해 두겠다" 며 일부를 구현하지 마라.
- 계획서에 실제 회원 이름·연락처를 쓰지 마라.
- 승인이 필요 없는 작은 작업에 계획서를 만들어 번거롭게 하지 마라.
