버그를 고친다. 증상을 없애는 게 아니라 **원인**을 고친다.

증상: $ARGUMENTS

> 인자에 `docs/PLANS/…md` 계획서가 있으면 그 상태가 `승인됨` 인지 확인하고 3번(수정 계획)을 건너뛴다. `초안` 이면 멈추고 승인을 요청한다.

## 절차
1. **재현** — 증상을 "화면 / 행동 / 기대 / 실제" 로 다시 쓴다. 불명확하면 질문 1개만.
2. **원인** — `debugger` 에이전트로 근본 원인을 받는다. 확신도가 "낮음" 이면 사용자에게 추가 정보(오류 화면 캡처, 기기, 오프라인 여부)를 요청한다.
3. **수정 계획** — `plan-gate` 스킬 1번 표에 **하나라도 해당되면**(개인정보·서버·삭제·결제·로그인·배포 설정·큰 변경) 원인·수정 범위·위험·되돌리는 법을 `docs/PLANS/오늘날짜-제목.md` 에 저장하고 요약을 보여 준 뒤 **승인 전에는 고치지 않는다**. 해당 없으면 "어느 파일의 무엇을 바꾼다" 한 줄만 보여 주고 진행한다.
4. **실패 테스트** — 로직 버그면 `tester` 로 재현 테스트를 먼저 만든다(지금은 실패해야 정상).
5. **수정** — 최소 범위로 고친다. 고치면서 다른 곳을 "겸사겸사" 바꾸지 않는다.
6. **확인** — 테스트 통과, `node --check`. 화면 버그면 `docs/TESTING.md` 3번 표에 점검 항목 추가.
7. **검토** — `reviewer`. 같은 원인의 다른 버그가 debugger 보고에 있으면 BACKLOG 에 적는다.
8. **커밋** (계획서가 있으면 상태를 `완료` 로) — `fix: {증상 요약}`.

## 보고 형식
```
## 고침: {증상}
**원인**: (한 줄, 쉬운 말)
**고친 곳**: 파일:함수
**확인하는 법**: 폰에서 …
**재발 방지**: 테스트 {파일} / 점검표 #{번호}
```
