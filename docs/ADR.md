> "**왜** 그렇게 정했나"를 남긴다. 나중에 "이걸 왜 이렇게 했지?" 할 때 다시 논의하지 않기 위해서다.
> 한 번 정한 것은 바꾸지 않는 게 아니라, **바꿀 때 새 ADR을 추가**하고 옛것에 "대체됨"을 적는다.

## 공통 ADR (AYOAJEYO 모든 프로젝트 기본값 — 바꿀 이유가 있을 때만 새 ADR로 덮어쓴다)

### ADR-000-1: 빌드 도구 없는 HTML + CSS + 순수 JavaScript
**결정**: React·Next.js 같은 프레임워크와 번들러를 쓰지 않는다.
**이유**: 파일을 열면 그대로 코드가 보여 초보자가 이해·수정하기 쉽다. 빌드 실패가 없다. GitHub Pages 에 바로 올라간다.
**트레이드오프**: 화면이 매우 복잡해지면 코드가 길어진다. → 그때 ADR 로 다시 결정.

### ADR-000-2: 배포는 GitHub Pages
**결정**: `main` 브랜치 push 가 곧 배포.
**이유**: 무료, HTTPS 기본(카메라·위치 권한에 필요), 별도 서버 관리 없음.
**트레이드오프**: 서버 코드를 못 돌린다 → 서버 로직이 필요하면 Supabase Edge Function.

### ADR-000-3: 데이터는 기기 우선, 서버는 필요할 때 Supabase
**결정**: 처음엔 기기(IndexedDB/localStorage)에만 저장. 여러 기기·여러 사람이 같은 데이터를 봐야 할 때 Supabase 를 붙인다.
**이유**: 개인정보가 기기 밖으로 나가지 않는 게 가장 안전하고, 회원가입 없이 바로 쓸 수 있다.
**트레이드오프**: 폰을 바꾸면 데이터 이전이 필요 → 내보내기/가져오기 기능을 v1 에 넣는다.

### ADR-000-4: 사진은 축소해서 저장, 원본은 보관하지 않음
**결정**: 촬영 즉시 긴 변 1600px·JPEG 품질 0.85 로 줄여 저장.
**이유**: 측정에는 충분한 해상도이고, 저장 공간·업로드 비용이 1/5 이하.
**트레이드오프**: 고해상도 원본이 필요한 용도에는 부적합.

### ADR-000-5: 디자인은 네이비 단일 포인트의 심플 스타일
**결정**: `docs/UI_GUIDE.md` 기본값 사용. 프로젝트마다 색을 새로 정하지 않는다.
**이유**: 아요바디요 제품군이 한 회사 제품으로 보이게. 결정 시간 절약.
**트레이드오프**: 개성 있는 비주얼은 포기.

### ADR-000-6: 버전은 네 곳 동시 갱신, 배포는 `/ship` 으로만
**상태**: 일부 대체됨(→ ADR-012: 이 프로젝트는 **두 곳 + CHANGELOG**). 배포를 `/ship` 으로만 하는 부분은 그대로 유효하다.
**결정**: APP_VERSION · manifest · sw.js CACHE_VERSION · CHANGELOG 를 `/ship` 이 함께 올린다.
**이유**: 하나라도 빠지면 사용자 폰에 이전 화면이 남는 사고가 반복됐다.
**트레이드오프**: 급한 수정도 `/ship` 절차를 거쳐야 한다(약 2분).

### ADR-000-7: 테스트는 계산 로직에만 자동, 화면은 폰 수동 점검표
**결정**: `js/logic/` 은 `node --test` 로 자동 검사. 화면은 `TESTING.md` 의 점검표를 실제 폰에서 손으로 확인.
**이유**: 카메라·터치·인쇄는 자동화 비용이 너무 크다. 로직은 자동화 비용이 거의 없다.
**트레이드오프**: 화면 회귀(예전 버그 재발)를 사람이 잡아야 한다.

### ADR-011: 계산 로직을 `js/logic/` 로 하나씩 분리하고 자동 테스트
**상태**: 채택 (2026-10-15)

**결정**: 화면을 모르는 순수 함수부터 `js/logic/*.js` 로 옮긴다. 파일은 브라우저(`window.AYO_LOGIC`)와 Node(`require`) 양쪽에서 쓰이게 만들고, index.html 에는 같은 이름의 한 줄짜리 연결 함수만 남긴다. 테스트는 `npm test`(= `node --test "tests/**/*.test.js"`). 새 파일은 `sw.js` SHELL_FILES 에도 넣는다(오프라인).
**첫 대상**: `scolJudge`(거북목 CVA·척추 균형 ATR·기울기 판정) → `js/logic/judge.js`.
**이유**: 한 번에 다 옮기면 14,000줄을 건드려 위험하다. 결과가 정해진 계산부터 작게.
**대안**: 전체 모듈 분리·번들러 도입 — 빌드 없음 원칙(ADR-000-1)과 위험 때문에 안 함.
**트레이드오프**: 파일이 하나 늘어 네트워크 요청 1회 추가. 새 index.html 만 받고 judge.js 를 못 받은 순간(새 서비스워커 설치 전 불안정한 연결)에는 판정 화면에서 오류가 날 수 있다.
**영향받는 파일**: js/logic/judge.js, tests/judge.test.js, package.json, index.html, sw.js
**진행 기록**: 2026-10-16 v283 — `romJudge`·`scoreBand` 도 `judge.js` 로 이동(그대로 복사, 동작 변화 없음). 리포트 '한눈에 보기' 를 위해 `report-timeline.js`(회차 시계열·KPI·상태표·아령 행)·`report-charts.js`(차트 좌표·SVG) 추가. 테스트 108개.

### ADR-012: 버전은 두 곳 + CHANGELOG — 앱 번호와 서비스워커 번호를 따로 센다
**상태**: 채택 (2026-10-15) — 공통 ADR-000-6 의 "네 곳" 을 이 프로젝트에서 대체
**배경**: 공통 ADR-000-6 은 `js/app.js` 의 `APP_VERSION`, `manifest.json` 의 `version`, `sw.js` 의 `CACHE_VERSION`, CHANGELOG 네 곳을 올리라고 한다. 이 프로젝트에는 그 중 **세 곳이 실제로 없다**(버전은 `index.html` 안의 `APP_VER`, manifest 는 `manifest.webmanifest` 이고 version 칸이 없고, 서비스워커 변수 이름은 `VERSION`). 문서·명령어가 없는 파일을 가리켜 배포 때 혼동이 생겼다.
**결정**: 올리는 곳은 두 곳 + CHANGELOG 로 한다.
1. `index.html` 의 `APP_VER`(`"v267"`) = `docs/CHANGELOG.md` 맨 위 `## vNNN` — 같은 번호
2. `sw.js` 의 `VERSION`(`"pma-v216"`) — 앱 번호와 **별개 카운터**로 배포마다 +1, 주석에 그때의 앱 버전을 적는다
`manifest.webmanifest` 는 version 칸이 없어 건드리지 않는다. 안드로이드 앱(TWA)을 새로 올릴 때만 Play `versionCode` 도 +1.
**이유**: 두 번호의 역할이 다르다. 앱 번호는 사용자가 화면에서 보고 말할 수 있는 번호, 서비스워커 번호는 폰에 남은 캐시를 버리게 하는 스위치다.
**대안**: 두 번호를 같은 값으로 통일 — 지금 번호가 이미 벌어져 있어(v267 vs pma-v216) 맞추는 과정에서 캐시가 꼬일 위험이 있어 안 함.
**트레이드오프**: 올릴 숫자가 두 개라 손으로 하면 빠뜨리기 쉽다 → `/ship` 이 둘을 함께 올리고 `/status` 가 일치를 점검한다.
**영향받는 파일**: docs/RELEASE.md, .claude/commands/ship.md, .claude/commands/status.md, .claude/commands/rollback.md, .claude/skills/pwa-release/SKILL.md, docs/GLOSSARY.md

### ADR-013: 목 굴곡·신전·측방굴곡을 보조선 방식으로 (측정 정의 변경)
**상태**: 채택 (2026-10-16) — 계획서 `docs/PLANS/2026-10-16-목-굴곡-보조선-측정.md`
**배경**: 목 각도를 '목관절 → 정수리' 선으로 쟀는데, 정수리는 머리 모양·머리카락·자세에 따라 흔들려 회차마다 값이 튀었다. 발목(v266)은 이미 보조선 방식으로 바꿔 안정적이다.
**결정**: 세 동작 모두 ①선 = 목관절 → 화면 위쪽 세로 기준선(자동), ②선 = 얼굴 선, 각도 = ①선 ↔ ②선과 평행하게 목관절을 지나는 파란 보조선.
- 굴곡·신전(옆 촬영): ②선 = 턱 앞 → 이마 앞
- 측방굴곡(정면 촬영): ②선 = 턱끝 → 정수리
- 정상값은 세 동작 모두 45°(전에는 굴곡·신전 90°)
- 기준각 `off`: 목 0°(바르게 선 자세가 0°), 발목 90°(직각이 0°) — `romAuxGeo` 가 동작 정의에서 읽는다
**이유**: 얼굴 앞 윤곽은 사람 실루엣에서 자동으로 잡히고 머리카락에 덜 흔들린다. 발목과 같은 장치를 쓰므로 새 코드가 거의 없다.
**대안**: 정수리 기준 유지 + 보조선만 표시 — 보기에만 달라지고 흔들림은 그대로라 안 함.
**트레이드오프**: 같은 '목 굴곡'인데 옛 기록(정수리 기준)과 새 기록(얼굴 선 기준)의 숫자 기준이 달라 회차 비교에서 값이 튈 수 있다. 옛 기록은 `romAuxLegacy`(점 3개)로 옛 방식 그대로 열리고 값도 바뀌지 않는다.
**영향받는 파일**: index.html(ROM_JOINTS 목, ROM_PTNAME·ROM_PART·ROM_DERIV, romGet, romRefine, romAuxGeo, romDefaultPts, romPlace, romFixVUp, ROM_GD, openRomGuide), tests/rom-aux.test.js, docs/TESTING.md

### ADR-014: 측정 비우기는 앱 안에 두고, 백업 없이는 실행되지 않게 한다
**상태**: 채택 (2026-10-16) — 계획서 `docs/PLANS/2026-10-16-측정기록-초기화-사진유지.md`
**배경**: 측정법이 여러 번 바뀌어, 지금까지 찍은 사진을 최신 방법으로 다시 재고 그 과정을 자동 인식 학습에 쓰고 싶다. 사진은 그대로 두고 측정만 비워야 한다.
**결정**: 관리자 화면에 '측정 비우기(사진 유지)' 를 둔다. ① '비우기' 직접 입력 ② 확인 창 — 두 단계를 통과해야 돌아가고, 한 번 실행하면 `ayo_wipe_done` 에 날짜를 남긴다. **단추를 잠그는 기준은 '한 번 실행했는가' 가 아니라 '남은 측정 기록이 0건인가' 다**(v277). 예전 측정값은 보관하지 않고, **백업도 조건으로 걸지 않는다**(2026-10-16 사용자 결정: 목적이 사진 재측정·학습이라 옛 측정값을 되살릴 이유가 없음). 백업 단추는 '선택' 으로 남겨 둔다.
**중요**: 이 결정은 이 기능에만 해당한다. 설정의 '내 데이터 내보내기·불러오기', 백업 알림, 서버 저장(동기화)은 그대로 유지한다.
**이유**: 개발자 도구나 수동 SQL 로 지우면 동기화 큐를 건너뛰어 다른 기기가 옛 값을 되살린다. 앱 안에서 `rawPut` 으로 지워야 서버와 다른 기기까지 같은 상태가 된다.
**대안**: ① 예전값을 따로 보관 — 사용자가 필요 없다고 결정 ② 일괄 자동 재측정 — 사진 수백 장에 인식을 연속으로 돌리면 중단 위험이 크고, '자동 인식 → 사람이 수정' 쌍이 학습 자료로 더 좋아서 안 함.
**트레이드오프**: 실행하면 지난 회차의 각도·점수를 다시 볼 수 없다(사진은 남는다). 되돌리려면 사용자가 따로 받아 둔 백업 파일이 있어야 한다.
**v277 보완 (2026-10-16)**: 실행했는데 측정값이 그대로 보이는 일이 있었다. 원인이 될 수 있는 세 가지를 모두 막았다.
- ① **화면이 안 다시 그려짐** — `rawPut` 은 `dbPut` 과 달리 캐시를 비우지 않아 목록·리포트가 옛 숫자를 그대로 보여줄 수 있다 → 실행 끝에 `romCache`·`romRenderCache`·`laCache` 를 비우고 `syncRefresh(true)` 로 다시 그린다.
- ② **일부만 비워졌는데 단추가 잠김** — 저장이 실패한 기록이 있어도 `ayo_wipe_done` 이 걸려 다시 실행할 수 없었다 → 남은 건수로 잠금을 판단하고, 결과 안내에 실패 건수를 따로 적는다.
- ③ **비울 것이 애초에 없었는지 알 수 없음** — 이 기기에 기록이 안 받아져 있으면 '0건 비움' 이 정상처럼 보인다 → 칸을 열 때 `wipeLeftCount` 로 **남은 건수 + 전체 건수**를 항상 표시한다.
**규칙(v277 리뷰에서 확인)**: 남은 건수를 세는 함수(`wipeRecLeft`·`wipeRomTodo`)는 `wipeRun` 이 '비울지 말지' 를 정하는 **바로 그 기준**이어야 한다. 두 기준이 갈리면 남은 건수가 영원히 0 이 되지 않아 잠금이 안 걸리고, 고치려던 "비웠는데 그대로" 가 다시 생긴다. 특히 **사진이 없는 ROM 기록**(`delete upd.img` 로 각도만 고친 예전 회차)은 다시 잴 수 없어 비우지 않으므로, 잠금 기준에서 빼고 `noPic` 으로 건수만 알린다. 실행 중에는 `wipeBusy` 로 재진입을 막는다.
**v279·v280 보완 (2026-10-16)**: 체형분석의 측정점이 기록이 아니라 **사진 묶음 안**(`blobs` 의 `photos.front.points`)에 있다는 사실이 늦게 드러났다. 사진은 필요할 때 서버에서 받아오므로(`blobFetch`), 사진이 안 내려온 기기에서 비우면 기록만 비워지고 서버 사진에 옛 점이 남아 **나중에 그 사진을 받을 때 옛 점이 되살아난다**.
- v279: 기기에 없는 사진을 `blobFetch` 로 받아서 지운다. 못 받으면 그 기록을 손대지 않는다. → **로그인·온라인이 필요하고 통신량이 크다**(사진을 받고, 점을 지운 사진을 다시 올린다). 안내에 '와이파이에서' 를 넣었다.
- v280: v279 가 **ADR 의 "세는 기준 = 비우는 기준" 규칙을 양방향으로 깼다**. ① 이미 한 번 비운 기록은 값이 null 이라 0건으로 세어져 단추가 잠기고, 정작 그 기록의 사진 점은 못 지운다 ② 영구히 못 받는 사진이 있으면 건수가 영원히 0 이 안 된다. → 점을 끝낸 기록에 `pxWiped` 를 남기고 `wipeRecLeft(r) = 값 || (blob && !pxWiped)` 로 두 기준을 다시 한 함수로 합쳤다. 서버에도 사진이 없으면 `pxGone` 으로 끝낸 것으로 보고 잠금 기준에서 뺀다(ROM 의 `noPic` 과 같은 취급). 덜 받아진 묶음(`blobHasRefs`)은 `syncPush` 가 업로드를 버리므로 반드시 다시 받아서 지운다.
