기능 하나를 끝까지 만든다. 사용자는 코딩 초보다. 각 단계의 결과를 짧게 보여 주고, **결정이 필요한 곳에서만** 멈춘다.

기능: $ARGUMENTS

> 인자에 `docs/PLANS/…md` 계획서가 있으면 그 파일이 설계다. 상태가 `승인됨` 인지 확인하고(`초안` 이면 멈추고 승인 요청) 2번 설계를 건너뛰되, 계획서의 단계 순서대로 구현한다.

## 절차
1. **파악** — `CLAUDE.md`, `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/DATA.md` 와 관련 코드를 읽는다. 화면이 있는 기능이면 `docs/TASTE.md` 와 (있으면) `design-system/styleguide.html` 도 읽는다. 인자에 `design/…html` 시안이 있으면 그 시안대로 만든다. 이 기능이 PRD 범위 밖이면 먼저 말한다.
2. **설계·계획** — `architect` 에이전트로 설계안을 받는다. `plan-gate` 스킬 1번 표에 **하나라도 해당되면** 설계안을 `docs/PLANS/오늘날짜-제목.md` 계획서로 저장하고 요약을 보여 준 뒤 **승인을 받을 때까지 구현하지 않는다**. 해당 없으면 한 줄 계획만 보여 주고 진행한다.
3. **데이터** — 새 필드가 있으면 `docs/DATA.md` 에 먼저 추가한다(등급·보관·삭제 포함).
4. **테스트 먼저** — 계산 로직이 있으면 `tester` 에이전트로 실패하는 테스트를 만든다.
5. **구현** — 단계별로 만든다. 화면은 `clean-ui`(규칙)·`ui-polish`(다듬기)·측정 데이터면 `measure-viz` 스킬을 따르고, 모양은 견본에서 복사한다. 그 밖에 관련 스킬을 따른다. 한 단계 끝날 때마다 `node --check`·테스트를 돌린다.
6. **검토** — `reviewer` 에이전트. 🔴 가 있으면 고치고 다시 검토(최대 2회). 개인정보를 다루면 `privacy-guard`.
   화면이 바뀌었으면: `python scripts/screenshot.py {화면 파일} [--hash "#화면"]` 로 390px 사진을 찍고(로그인해야 보이는 화면은 배포 뒤 `app-capture` 스킬로) → `ui-checker`(규칙 위반, 🔴 는 고침) → `ui-designer`(개선안). 개선안 중 "높음" 이고 UI_GUIDE·TASTE 와 부딪히지 않는 것은 반영하고, 반영했으면 **다시 찍어 `ui-checker` 를 한 번 더** 돌린다. 나머지는 보고에 적어 사용자가 고르게 한다. 캡처 도구가 없다고 나오면(끝 번호 3) 사진 없이 코드로 점검하고 보고에 "캡처 없음" 이라고 적는다.
7. **문서** — `docs-keeper` 에이전트로 CHANGELOG(미출시 항목)·DATA·TESTING(수동 점검 항목)·BACKLOG 갱신. 계획서가 있으면 상태를 `완료` 로 바꾸고 실제와 다른 점을 적는다.
8. **커밋** — `feat: {기능 요약}` 로 커밋. push 는 하지 않는다(배포는 `/ship`).
9. **보고** — 아래 형식.

## 보고 형식
```
## 완료: {기능}
**달라지는 것**: (사용자 입장 2줄)
**바뀐 파일**: 표 | 파일 | 무엇을 |
**직접 확인하는 법**: 폰에서 {화면} → {행동} → {보여야 할 것}
**검토 결과**: reviewer ✅ / privacy-guard ✅ / ui-checker ✅ / ui-designer 반영 n건 (문제 있으면 요약)
**화면 사진**: .shots/{파일}.png (캡처 도구가 없으면 "없음")
**더 다듬을 수 있는 점**: ui-designer 개선안 중 반영 안 한 것 (번호로 골라 달라고 안내)
**다음**: `/ship` 으로 배포하거나, 더 고칠 점을 말씀해 주세요.
```

## 금지
- 요청하지 않은 기능을 끼워 넣지 마라. 떠오른 아이디어는 BACKLOG.md "다음" 에 적어라.
- 테스트를 통과시키려고 테스트를 약하게 고치지 마라.
